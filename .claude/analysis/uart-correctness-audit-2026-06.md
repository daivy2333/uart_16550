## 1. 审计目标与结论

本次审计以 `de8cd8b`、`7c1e9f4`、`62755f0` 暴露的 TX 唤醒遗漏、waker 注册竞态和 busy-poll 为线索，检查同步核心、异步 copier、ISR、ring buffer 和 `embedded-io-async` 适配。

结论：当前实现仍有同源问题。核心原因不是单个调用顺序，而是以下约束没有被类型和状态所有权强制表达：

1. waker 和 IER 状态必须按 UART 端口隔离；
2. SPSC ring 的 producer/consumer 必须保持唯一所有权；
3. 异步等待必须使用“注册 → 重新检查条件 → Pending”的闭环；
4. 寄存器访问必须统一经过 backend，保留 stride 和架构访问语义；
5. 临时硬件状态修改必须在所有错误路径恢复。

审计确认 2 项 Critical、7 项 High、3 项 Medium 风险。建议在继续性能优化前先完成 P0/P1 正确性修复。

## 3. Critical 发现

### 3.1 F1：SPSC 唯一所有权未被 API 保证

`RingBufRx`/`RingBufTx` 在 `src/async_/ring_buffer.rs:50-55,194-197` 手工实现 `Send + Sync`，并通过 `UnsafeCell` 在 `&self` 方法中生成同一 `Reader`/`Writer` 的 `&mut` 引用。安全注释依赖“只有一个 producer/consumer”，但公开 API 可以直接破坏此前提：

- `AsyncUartWriter` 可 `Clone`（`src/async_/device_ops.rs:87-93`），多个 writer 可并发调用 `tx.push()`；
- `AsyncUartReader::new(Arc<...>)` 是公开构造器，可创建多个 reader；
- `AsyncUartDriver.rx` 和 `.tx` 为公开字段；
- `start_rx_copier()` / `start_tx_copier()` 可重复调用，创建多个 endpoint 使用者。

这不是一般逻辑竞态，而是可能同时构造指向同一值的多个可变引用，违反 Rust 别名规则并导致 UB。

建议：把底层 ring 明确拆成不可复制的 Producer/Consumer capability；driver 私有持有 copier 端，reader/writer 各取得唯一端；如确需 MPSC/MPMC，改用支持该并发模型的数据结构或显式锁。移除依赖调用方自律的 `unsafe impl Sync`，并让 copier 启动具备一次性状态。

### 3.2 F2：异步 I/O 方法实际上不会等待

`src/async_/device_ops.rs:56-58` 的 `read()` 直接 pop，ring 空时对非空 buffer 返回 `Ok(0)`；`write()` 在 ring 满时返回 `Ok(0)`；`flush()` 无条件立即成功。

这与 `embedded-io-async 0.6.1` 契约冲突：非 EOF 的空读应等待至少一个字节；非空写入不应返回 `Ok(0)`；flush 应保证中间缓冲内容到达目的地。直接后果包括：

- `read_exact()` 把暂时无数据解释为 EOF；
- `write_all()` 遇到 ring 满会 panic（依赖默认实现显式检查 `Ok(0)`）；
- flush 返回时 TX ring、FIFO 或 shift register 仍可能有数据。

建议：实现基于 ring waker 的可取消等待；读写采用 register→recheck 模式；flush 至少等待 TX ring 为空，并按 API 语义决定是否继续等待 `LSR::TRANSMITTER_EMPTY`。错误类型不能继续是 `Infallible`，除非所有不可恢复状态确实被等待机制消除。

## 4. High 发现

### 4.1 F3：TX ring 仍有与 M4 同构的丢唤醒窗口

`tx_copier_loop()` 在 `src/async_/driver.rs:234-240` 先 `pop_batch()`，发现空后才 `register_waker()`。若 producer 在两者之间 push 并 wake，唤醒无人接收；随后 copier 返回 Pending，ring 中已有数据但不会再产生新 wake，输出永久停滞。

正确模式是：先注册 waker，再检查/重查 ring；如果条件在注册后已成立则继续处理，否则 Pending。只把“ISR waker 注册”移到 enable 前并不能覆盖 ring producer/consumer 的等待竞态。

### 4.2 F4：全局 waker 破坏多端口隔离

`src/async_/isr.rs:15-21` 定义全局 `RX_WAKER`、`TX_WAKER`、`DRAIN_WAKER`。任意端口的 copier 注册都会覆盖同类端口之前注册的 waker；任意 UART IRQ 又会唤醒最后注册者。单端口部署暂不触发，但 crate 的构造 API 支持多个 UART 实例，因此该限制既未声明也未编码。

建议把 waker 放入 per-port IRQ state，并由 ISR 接收该 state；`DRAIN_WAKER` 当前只有 wake、没有任何注册调用，也应在实现 drain future 时归入同一状态对象。

### 4.3 F5：ISR 寄存器访问与 backend 语义分叉

`IsrRegisters` 仅保存 `NonNull<u8>`，在 `src/async_/isr.rs:43-93` 直接使用 `base + offset` 和 `read_volatile/write_volatile`：

- 忽略 `MmioBackend` 支持的 stride；stride=4 时 ISR/IER/LSR 地址全部错误；
- 无法支持 PIO backend；
- 绕过 aarch64 backend 强制使用 `ldrb/strb` 的架构约束。

建议让 ISR 使用与同步核心相同的 backend-aware accessor，或建立专用但完整携带 address kind、stride 和 arch access primitive 的 `IrqRegisters`。

### 4.4 F6：IER 更新不是原子状态转换

`disable_rx_intr()` / `disable_tx_intr()` 对 `cached_ier` 执行 Relaxed load→计算→store，再写硬件。若 task/另一个 CPU 同时 enable 另一位，旧值 store 会覆盖新位。Atomic 只保证单次读写不撕裂，不保证复合读改写原子。

建议统一由 per-port IRQ state 串行化 IER 更新；cache 使用 `fetch_update`/CAS 或 IRQ-safe lock，硬件写入必须与成功的 cache 状态转换属于同一临界区。外部 `fn()` enable callback 使一致性无法由 driver 验证，应替换为有状态接口。

### 4.5 F7：部分中断源不清除

ISR 只处理 RX ready/timeout 和 THR empty（`src/async_/isr.rs:110-123`）。但公开 IER/Config 支持 `RECEIVER_LINE_STATUS`、`MODEM_STATUS` 和 DMA 位。前两者分别需要读取 LSR/MSR 清除；当前 `_ => {}` 会留下 pending source，在 level-triggered IRQ 上可反复进入中断。

建议循环读取 ISR 直到 no-pending，并显式处理或禁用每个可启用源；未知/不支持源应有可观测计数和防风暴策略。

### 4.6 F8：`init()` 不是失败原子的

`src/lib.rs:414-465` 在参数验证前更新 `self.config`、修改 SPR、清零 IER并设置 DLAB。`calc_divisor(...)?` 失败时直接返回，DLAB 保持置位。此后 offset 0/1 的 DATA/IER 操作实际访问 DLL/DLM，设备进入难以诊断的损坏状态。

建议先在纯计算阶段完整验证 config，再写硬件；写入阶段使用 guard 保存并恢复 LCR/IER/MCR，只有全部成功才提交 `self.config`。SPR 探测也应恢复原值。

### 4.7 F9：loopback 错误路径不恢复 MCR

`test_loopback()` 仅在成功尾部恢复 MCR（`src/lib.rs:602-603`）。此前的 `?` 和内容不匹配 `return Err(...)` 都会跳过恢复，使设备保持 `MCR::LOOP_BACK`。函数还会重置 FIFO，且无限等待路径无超时。

建议使用 RAII guard 保证 MCR/IER/FCR 相关状态在所有退出路径恢复，并提供有界超时版本供真实硬件诊断。

## 5. Medium 发现与测试缺口

### 5.1 F10：NAPI 路径没有真正的调度预算

RX copier 只改变单次 batch 大小；只要 `receive_bytes()` 持续返回数据，`poll_fn` 就持续 Ready，外层 loop 可在一次 executor poll 中重复执行。持续串口流量下任务可能长期不让出。建议增加总 budget，耗尽后显式 yield/自唤醒 Pending，并用指标验证公平性。

### 5.2 F11：公开计算 API 的错误模型不完整

`calc_baud_rate()`、`calc_frequency()`、`calc_divisor()` 对零值和 prescaler 范围只做 `debug_assert`；release 下仍可能除零或算术溢出。`calc_divisor()` 对超出 `u16` 的结果 `unwrap()`。这些输入可由公开 `Config` 提供，因此 `init() -> Result` 仍可能 panic。

建议使用 checked arithmetic，并把 zero/range/overflow 纳入错误枚举。

### 5.3 F12：现有测试会制造错误安全感

`red_isr_wake_lost_between_enable_and_register` 手工执行“wake 后 register”并断言 wake 丢失，没有调用 `rx_copier_loop()`，因此实现再次改回错误顺序时测试仍可通过。ring 测试复用可变 static ring，在并行 test runner 下也可能互相重初始化。

建议用可插桩 enable callback 在真实 poll 路径注入 IRQ；每个测试使用独立 storage；增加 loom/受控调度测试覆盖 register/recheck、IER CAS 和多 producer 禁止性。

## 6. 建议修复顺序

1. **P0 / 内存安全**：重构 ring endpoint 所有权，移除可并发别名路径；限制 copier 只能启动一次。
2. **P0 / API 语义**：重写 async read/write/flush 的等待状态机并添加契约测试。
3. **P1 / IRQ 状态**：per-port waker + backend-aware ISR + 原子/锁保护 IER；完整清除中断源。
4. **P1 / 状态恢复**：对 `init()`、`test_loopback()` 引入预验证与 RAII rollback。
5. **P2 / 调度与测试**：NAPI budget/yield，多端口、stride=4、aarch64、SMP 交错和失败注入测试。
